## 만들려는 경험

책상 사진 한 장을 넣으면 사진과 대략 닮은 voxel 스타일 3D 장면을 만들고, 사용자가 물건별로 선택·제외·추가하거나 위치·크기를 고친 뒤 확정하는 앱이야. 방과 책상이 화면의 중심이고 패널은 보조 역할을 해. 정밀 3D 스캔이 목표는 아니지만, 주요 물건의 종류·개수·상대 크기·좌우/앞뒤 관계·받침 관계는 납득할 수 있어야 해. 사용자가 처음부터 배치를 다시 만드는 수준이면 곤란해.

React/TypeScript/Three.js 앱이고, Meta `muse-spark-1.3`이 구조화된 물체 목록을 반환해. 앱은 정해진 geometry template 또는 제한된 box 조합으로 렌더링해. 현재 모델은 종류, 좌표, scale, supportId, 사진 속 대략적인 imageRegion을 함께 제안하고, 앱은 검증·받침 순서 정렬·제한된 높이 보정을 수행해. 사진 추정, 사용자 보고, 실제 하드웨어 관측을 구분하며 최종 반영에는 사용자 확인이 필요해.

## 읽을 자료와 코드

1. `README.md`, `docs/PHOTO_REVIEW.md`, `docs/PHOTO_EVALUATION.md`: 목표, 구현 범위, 실제 호출 결과와 한계.
2. `server/meta.ts`, `src/domain/sceneProposal.ts`: 모델 지시문, 출력 schema, 검증, draft 생성과 적용.
3. `src/domain/workspace.ts`, `src/domain/geometry.ts`, `src/domain/spatial.ts`: 데이터 구조, template 크기, 접촉·받침·충돌·배치 로직.
4. `src/components/PhotoPanel.tsx`, `src/components/ScenePreview.tsx`, `src/domain/photoInput.ts`: 시간 제한, 사진 처리, 사용자 수정 흐름.
5. `scripts/replay-photo-placement.ts`와 관련 domain/browser tests: 재현 가능한 문제와 기존 테스트가 실제로 보장하는 범위.

## 현재 관찰된 문제

같은 사진·workspace·빈 사용자 설명으로 이전 버전은 22.601초에 물체 12개를 반환했어. 개선 버전은 기본 35초 제한에서 시간 초과가 났고, 별도로 승인한 테스트에서만 90초로 늘리자 38.887초에 19개를 반환했어. 당시 제품의 서버 제한은 35초, 브라우저 제한은 40초였어. 현재 사진 분석 제한은 서버 60초, 브라우저 65초이며 새로운 실 API 호출로 검증하지 않았어.

새 결과에서 손목 받침대·트랙패드·태블릿·조명 2개·노트북 스탠드가 따로 나왔지만, 이전에 있던 물건 일부는 빠졌어. JSON 검증은 통과했지만 배치 문제 때문에 적용은 차단됐어. 단일 사진 사례이고 프롬프트·schema·template·앱 로직을 함께 바꿨으므로 품질 향상이나 원인을 일반화할 수는 없어.

실제 응답에서 뽑아 개인정보를 제거한 작은 재현 사례가 있어. 가능하면 `node --import tsx scripts/replay-photo-placement.ts`로 확인해줘. 실행할 수 없다면 정적 분석과 실행 관찰을 구분해줘.

- 모델 설명에는 키보드가 매트 위에 있다고 쓰였지만 `supportId`는 책상이었어. 받침 대상만 매트로 바꾸니 그 작은 장면의 충돌이 사라졌어.
- 손목 받침대가 키보드와 너무 가까워 겹쳤어. Z 간격만 늘리니 그 충돌이 사라졌어.
- 노트북 밑면이 스탠드보다 조금 넓으면 앱의 전체 접촉면 검사에서 탈락하고 높이 보정도 건너뛰어. 높이만 맞추면 경고 3개가 받침 경고 1개로 줄어들었어.
- 이전처럼 매트를 바닥으로 보내는 문제는 수정했지만, 현재 로직은 X/Z와 scale을 유지해 전체 배치를 해결하지는 못해.

이것은 현재 진단이며, 코드로 반박하거나 보완해도 좋아. 사진 원본이 없으므로 실제 물체 인식률이나 시각적 충실도를 직접 평가할 수 없는 부분은 구분해줘.

## 조언받고 싶은 결정

현재 구조의 작은 규칙 수정, 별도 제약 기반 배치 단계, 사진 영역과 소수의 사용자 기준점을 활용하는 방식 중 어떤 접근이 지금의 MVP에 적절할까? 다른 접근이 낫다면 포함해줘. “모델은 물체와 관계를 추론하고 앱은 좌표를 계산한다”는 방향도 가설로 검토하고, 그 방향에 맞춰 결론을 정하지 말아줘.

특히 아래를 구체적으로 다뤄줘.

- 모델과 앱이 각각 결정할 정보: 절대 좌표·상대 크기·supportId·좌우/앞뒤 관계·imageRegion·불확실성을 어느 단계에서 어떻게 사용할지. 필요한 최소 schema 예시도 제시해줘.
- geometry와 받침: 매트, 모니터 받침대, 노트북 스탠드, 모니터 조명처럼 접촉 방식이 다른 물건을 어떻게 처리할지. 허용할 돌출과 실제 관통을 구분하고, 자동 보정이 사진 배치를 과하게 바꾸지 않도록 어떤 제한을 둘지.
- 사용자 흐름: 일부 물건이 모호하거나 충돌할 때 어떤 질문과 수정 도구가 가장 적은 수고로 결과를 개선할지. 물건 수만 늘어나고 수정 부담이 커지는 상황을 어떻게 피할지.
- 지연 시간: 현재 사진 분석 서버 60초와 브라우저 65초 제한에서 안정적으로 결과를 보여주려면 출력량·단계 분리·점진적 표시·취소·재시도를 어떻게 설계할지. 단일 관찰을 근거로 예상 지연 시간이나 비용을 단정하지 말아줘.
- 평가: 합성 테스트 통과와 사진 품질을 분리해서, 적은 사진으로도 인식 누락/중복, 상대 배치, 받침/충돌, 사용자 수정량, 지연 시간을 비교할 수 있는 작은 평가 세트를 제안해줘.

답변은 핵심 진단과 권장 방향을 먼저 제시하고, 의미 있는 대안의 장단점, 최소 변경안, 이후 확장 순서로 작성해줘. 주요 진단은 파일과 함수에 연결하고, 우선순위가 높은 작업마다 수정 위치·기대 효과·검증 방법·실패 시 대안을 적어줘. 마지막에는 구현 에이전트가 바로 작업을 나눌 수 있는 계획과, 아직 내가 결정해야 하는 선택지만 정리해줘.
